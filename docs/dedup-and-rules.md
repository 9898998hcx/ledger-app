# 去重算法与分类规则

## 一、为什么要去重

一笔真实的消费往往会在两个地方各留一条记录：

```
微信账单：2026-10-04 12:20  美团外卖  -36.00   微信零钱
银行卡  ：2026-10-04 12:20  财付通-美团外卖  -36.00  快捷支付
```

如果直接相加，这笔钱会被算两次。而如果简单地"按金额去重"，又会误杀同一天同一金额的两笔真实消费（比如连续两次各 36 元的打车）。所以去重必须分层：**强标识优先，弱标识兜底，且只在跨源之间启用模糊匹配**。

## 二、三层去重

### 第 1 层：同一文件

文件内容先归一化（去 BOM、`\r\n` / `\r` 统一成 `\n`、去尾部空白），再算哈希。哈希已存在于 `import_batches` 且该批次成功导入过 → 整批跳过，不做任何写入。

若上一批导入结果为 0 行（失败），则删除该批次记录并允许重试，避免"一次失败永久挡住这个文件"。

实现：`domain/import.ts` 的 `normalizeContent` / `existingBatchResult`。

### 第 2 层：同源重复

- `source_trade_no`（平台订单号）已存在 → 跳过。数据库层用 `UNIQUE INDEX (source, source_trade_no)` 兜底。
- 没有订单号时用行哈希 `raw_hash` 判断。

**关键取舍**：同源之间**不做金额去重**。同一平台里"同一天、同一金额、同一商户"的两笔是真实存在的（比如连点两份外卖），只有订单号能区分它们。

### 第 3 层：跨平台模糊匹配

对候选记录要求同时满足：

| 条件 | 实现 |
| --- | --- |
| 金额相同 | 整数分完全相等 |
| 方向相同 | 都是 `expense` 或都是 `income` |
| 时间接近 | 相差 ≤ 1 天（`MS_PER_DAY`） |
| 商户相似 | 相似度 ≥ `MERCHANT_SIMILARITY_THRESHOLD = 0.6` |

命中后的处理：

- 已有记录是银行、新导入的是支付平台 → 新记录为主记录，旧银行记录标记 `is_mirror = 1`（`newPrimary`）。
- 已有记录是支付平台、新导入的是银行 → 新记录标记镜像（`newMirror`）。
- 微信 vs 支付宝 → 后导入者标记镜像。
- 镜像记录不重复计入统计，也不在支出页重复展示，但保留在库里，用于回答"这笔钱到底从哪张卡扣的"。

**额外捷径**：若银行流水的渠道归属（`domain/channel.ts` 从摘要里识别"微信 / 财付通 / 支付宝"）与支付平台记录一致，则跳过商户相似度判断，直接按「金额 + 方向 + ±1 天」认定为同一笔——因为渠道已经说明它们是同一笔钱。

实现：`domain/dedup.ts` 的 `matchExisting` / `buildDedupKey`，编排在 `domain/import.ts`。

## 三、商户相似度

```ts
merchantSimilarity('美团外卖', '美团外卖有限公司')     // 0.8（包含关系）
merchantSimilarity('财付通-美团外卖', '美团外卖')       // 命中 bigram Jaccard
merchantSimilarity('星巴克', '瑞幸咖啡')                // 0（低于阈值）
```

算法：

1. **规范化**：转小写、去掉中英文标点（`（）【】「」《》，。！？：；、-_/\|@#￥%^&*` 等）与所有空白。
2. **相等** → 1.0。
3. **一方包含另一方** → 0.8（覆盖「公司名 + 简称」的常见写法）。
4. 否则取字符 bigram 集合的 **Jaccard 系数**：`|A∩B| / |A∪B|`。

用 bigram 而不是编辑距离，是因为中文商户名多为 2–6 个字，bigram 对「同名不同后缀」「中间插字」更稳，也避免了编辑距离对长名字的偏好。

实现：`domain/merchant.ts`。同一套规范化函数也被"商户记忆"复用，保证分类与去重看到的是同一个 key。

## 四、分类规则

### 数据结构

`category_rules` 表：

| 字段 | 说明 |
| --- | --- |
| `priority` | 越小越先匹配 |
| `match_type` | `keyword`（包含匹配，忽略大小写）或 `regex` |
| `pattern` | 关键词或正则 |
| `category` / `subcategory` | 命中后归到的分类 / 子分类 |
| `enabled` | 是否启用 |

JSON 形态（`src/domain/rules/default-rules.json`）：

```json
{ "priority": 10, "matchType": "keyword", "pattern": "美团", "category": "餐饮", "subcategory": "外卖" }
```

### 匹配顺序

```
category_rules（按 priority 升序，命中即停）
        ↓ 未命中
merchant_rules（按规范化商户名精确匹配，来自用户手动纠正）
        ↓ 未命中
category = null（界面显示「其他」，原始用途照常展示）
```

- 规则匹配范围是「交易对方 + 商品说明」拼接后的文本。
- 非法正则不会中断流程：`try/catch` 后继续看下一条规则。
- 默认规则只在 `category_rules` 表为空时写入；「恢复默认规则」= 清空后重新种子，不会动 `merchant_rules`。
- 用户手动改分类 → 写入 `merchant_rules`，同商户下次自动归类（`hit_count` 记录命中次数）。

实现：`domain/classify.ts`、`domain/rules/seed.ts`、`src/app/rules-actions.ts`。

### 默认分类

`餐饮`（正餐 / 外卖 / 咖啡）、`交通`（打车 / 公交地铁 / 单车 / 火车 / 快递）、`购物`（日用 / 服饰 / 数码）、`居住`、`通讯`、`娱乐`、`医疗`、`教育`、`人情往来`、`退款`、`其他`——共 23 条默认规则。

## 五、统计口径

- 统计只计算 `is_mirror = 0` 且 `direction != 'neutral'` 的记录。
- 「全部」来源 = 微信 + 支付宝；银行卡需要显式选「银行」（因为银行流水天然包含转账、理财等非消费项，混在一起会让月度支出失真）。
- 收入页同理，「全部」只含微信 + 支付宝。
- 自己名下账户互转识别为 `neutral`，不进任何合计。
